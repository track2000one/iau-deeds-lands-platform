# خطة اعتماد صور ومرفقات السجل المركزي للمباني على Staging

> الحالة: مسودة؛ لا تُعدّ هذه الوثيقة إثباتًا للنشر أو نجاح الاختبارات التشغيلية.

## حالة البنية الحالية (3 نوفمبر 2026)

- Production في Railway project `intuitive-comfort`: خدمات IAU Deeds frontend/backend وقاعدة PostgreSQL تعمل من `main`.
- البيئة `iau-deeds-restore-test`: PostgreSQL فقط. هذه **ليست** Staging جاهزة لتجربة التطبيق؛ احتفظ بها لاختبارات الاستعادة ولا تربطها بالإنتاج.
- تنفيذ الصور والمرفقات في فرعي PR منفصلين:
  - Frontend: `track2000one/iau-deeds-lands-platform#130`
  - Backend: `track2000one/iau-deeds-backend#67`
- **ممنوع** توجيه رابط الاختبار إلى قواعد بيانات Production أو مجلد Google Drive الإنتاجي.

## شروط تجهيز Staging قبل أي نشر

1. إنشاء خدمات Frontend وBackend وPostgreSQL مخصصة للاختبار، مع التأكد من فصل التخزين عن Production.
2. تثبيت مصدر الخدمات على الفرع `feat/central-building-media-20261103` أو SHA محدد منه بدل `main`.
3. ضبط `DATABASE_URL` الخاص بالخلفية على PostgreSQL التجريبي فقط والتحقق منه قبل بدء التطبيق (لأن أمر بدء backend الحالي يتضمن `prisma db push`).
4. ضبط `GOOGLE_DRIVE_FOLDER_ID` على مجلد اختبار **مستقل** مع صلاحيات خاصة، وعدم استخدام ملفات إنتاجية فعلية أو بيانات أشخاص حقيقية.
5. إعداد `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` / `GOOGLE_OAUTH_REFRESH_TOKEN` باعتمادات مخوّلة لبيئة الاختبار فقط، دون طباعة قيمها في السجلات.
6. توجيه `VITE_API_URL` إلى Backend التجريبي وتقييد `CORS_ORIGINS` و`FRONTEND_URL` بنطاق الاختبار.
7. قبل النشر: النسخة الاحتياطية، أسماء الخدمات والنطاقات، فحص فصل قواعد البيانات، والتحقق من خلو الخدمات من أي إشارة إلى مشروع أو بيانات Production.
8. نشر Backend التجريبي أولًا بعد فحص المخطط؛ ثم Frontend التجريبي. عدم دمج فرعي PR أو تغيير مصادر خدمات Production تلقائيًا.
